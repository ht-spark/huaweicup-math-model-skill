# 华为杯数学建模报告写作

## 角色与边界

本技能负责把**已有、可追溯的建模成果**组织成符合当届规范的华为杯数学建模报告，并完成事实一致性、结构完整性和表达质量检查。

- 以当届组委会上传的规范为最高格式与工具使用依据；规范与本技能默认规则冲突时，始终服从规范。
- 只陈述题目、数据、模型说明、代码运行产物和建模证据能够支持的内容；不得补造模型、参数、实验、图表数值、结论、参考文献或验证结果。
- 不重新执行建模、调参或替代建模技能解决题目。发现证据不足时，输出待补充清单，而不是用猜测填补正文。
- 不按 A/B/C/D/E 题类别套用固定写法。报告结构由当前题目、实际建模路线与当届规范决定。

## 项目材料约定

`<项目根目录>` 指用户当前参赛项目，而非本技能所在目录。写作前先在项目中查找以下约定位置：

```text
<项目根目录>/
├── upload_material/                         # 只读：用户上传的原始材料
│   ├── 题目.*
│   ├── 数据1.*、数据2.*、...                 # 数量可变
│   └── 规范1.*、规范2.*、...                 # 数量可变；当届格式/工具规则等
├── modeling_output/                         # 只读：建模技能的成果
│   ├── 图片/
│   ├── 代码/
│   ├── 表格/
│   └── 说明文档/
│       ├── 输入材料清单.md
│       ├── 结果说明.md
│       └── 建模证据清单.yaml
└── report_output/                           # 本技能唯一可新建或写入的位置
```

材料文件的扩展名可以不同；`数据N`、`规范N` 的数量可以为零、一个或多个。不得修改、重命名、移动或覆盖 `upload_material/` 和 `modeling_output/` 中的文件。

`建模证据清单.yaml` 是写作的主索引：每个小问应至少能定位其任务要求、采用模型、可报告结论、已做验证及关联产物。`结果说明.md` 负责解释数值和产物含义，`输入材料清单.md` 用于核对使用了哪些输入。三者彼此冲突时，回查关联的代码、表格、图片或题目；无法判定时标为待核对，不自行裁决。

## 写作前核验

每次任务先执行以下核验，再开始成文：

1. 读取 `upload_material/题目.*`，识别问题、交付要求和术语边界。
2. 读取全部 `upload_material/规范N.*`，提取当届论文格式、匿名要求、文件格式、图表要求和人工智能工具使用限制。没有规范文件时，明确记录“未提供当届规范”，不可声称已符合当届全部细则。
3. 读取 `modeling_output/说明文档/输入材料清单.md`、`结果说明.md` 与 `建模证据清单.yaml`；建立“小问—模型—结论—验证—产物路径”的证据映射。
4. 仅在证据清单引用某一材料、或需核实具体矛盾时，按需读取相关的图片、代码或表格；不要无差别扫描全部原始数据和产物。完整报告或包含结果分析的章节，须枚举 `modeling_output/图片/` 和 `modeling_output/表格/` 中与该小问有关的候选产物，排除虚拟环境、缓存、审计中间件等非交付文件。
5. 对候选图片，确认其实际展示的变量、坐标轴、图例、关键标注和可支持的结论；对候选表格，确认字段、单位、口径与正文数字一致。不能读懂、没有图题/表题或不能支撑正文的产物不得装饰性引用。
6. 核对题目小问是否都有可追溯结论、关键数字是否有表格/代码/图像来源、验证是否真的已执行，以及未解决事项是否会影响写作请求。

如缺少题目、建模说明文档或必要证据：

- 对“完整报告”或“终稿”请求，先在 `report_output/待补充材料.md` 列出缺失项、影响的小问与所需证据，不输出伪完整报告。
- 对“大纲”或“指定章节”请求，可提供带 `【待补充】` 标记的结构和写作槽位；所有未证实内容必须保留占位，不能写成既成事实。

本技能采用“主入口 + 按需参考”的方式。先阅读本文件，再只加载当前任务需要的资源，避免把模板误当成事实来源。

| 摘要                           | `references/abstract.md`                                                                                               | `solution.md`、`validation.md`                                  |
| 问题重述                       | `references/problem-restatement.md`                                                                                    | `problem-analysis.md`                                             |

| 某小问的分析、建模、求解与结果 | `references/problem-analysis.md`、`references/modeling.md`、`references/solution.md`、`references/validation.md` | `data-processing.md`                                              |

`humanizer-chinese-math-modeling/` 是本技能已完整内嵌的去 AI 味模块，包含其自身说明、参考规则和校验脚本；调用它不需要用户额外安装任何技能。使用该模块时，严格保留题目术语、公式、变量名、单位、图表编号、数据、引用和结论边界，只改善表达的自然度、具体性和可读性。

## 报告组织规则

1. 以 `references/report-architecture.md` 为可伸缩骨架，根据题目删减、合并或增加必要部分；不要机械保留与题目无关的章节。
2. 报告主体通常覆盖：摘要与关键词、问题重述、假设与符号、总体思路（按需）、各小问的分析—建模—求解—结果、模型评价与总结、参考文献、附录。二级标题以实际内容命名，不使用空泛的“分析”“结果”堆叠。
3. 每个小问独立形成证据闭环：题目目标 → 数据/依据 → 方法与关键假设 → 求解或计算 → 结果解释 → 验证/适用边界 → 关联产物。
4. 误差指标、基线对比、约束满足、灵敏度、稳健性、情景或泛化检验，均放在对应小问的“求解与结果分析”中；只写已经执行且有证据的验证。没有可用验证时，说明其限制或列为待补充，不能虚构检验结论。
5. 摘要最后写，压缩呈现问题、核心方法、关键结论与最重要的验证信息；不得出现正文没有证据支撑的新结论。
6. 图、表、公式和附录均须在正文中被引用并解释其含义；图表路径和数值应能回溯到 `modeling_output/` 的产物。

## 图表采用与 Markdown 嵌入

图表是结果证据的一部分，不能只在正文写“见图 X”或只把源文件路径放进附录。对每个已完成、且建模产物中存在可用图或表的小问：

1. 依据“该图表能否直接支撑一个关键结论或验证”筛选，不要求把全部产物塞进报告，也不得为凑数量重复展示同一信息。
2. 当存在可解释结果机制、求解过程或验证结论的图片时，至少选用一幅最有信息量的图片；当存在能支撑关键数值、方案比较或验证的数据表时，在正文给出相应 Markdown 表。若图与表分别提供不同证据，应同时使用。
3. 将每个选中的图片的可发表版本（默认 PNG；格式规范另有要求时从其规定）复制到 `report_output/图片/`，并在 `报告.md` 中以相对路径真正嵌入，例如：

   ```markdown
   ![图 2 遮蔽距离随时间变化；红虚线为 10 m 阈值，阴影区为有效遮蔽区间。](图片/fig2_shielding.png)

   *图 2  云团中心到导弹—目标视线的距离。红虚线对应遮蔽阈值，阴影区说明有效遮蔽发生在 8.013–9.448 s。*
   ```

4. 将选中的原始数据表或其可复核副本保存至 `report_output/表格/`；正文 Markdown 表只能从该表或其他明确证据中逐项整理，表题、单位、统计/计算口径和来源必须写清。不得根据段落文字手工补造表格。
5. 图题解释“展示什么、为什么重要、读者应得出什么”，不重复坐标轴文字；表格后的文字解释主要发现，不能只罗列数值。
6. 若候选图表因分辨率、可读性、内容重复、与正文结论无关或当届规范限制而未采用，在 `写作审查.md` 说明原因。没有可用图表时也必须记录“未提供可采用图表”，而不是伪造图表。

## 执行流程

### 1. 明确任务与证据范围

识别用户请求属于完整写作、章节草拟、结构调整、事实一致性审查或语言润色。完成写作前核验，建立或更新报告证据映射；每一项叙述都标注其来源文件与对应小问。

### 2. 生成适配的大纲

依据题目、实际模型链条和当届规范，选择必要章节和二级标题。先确认每节将回答的问题、需要使用的证据和预期结论，再写段落。若一个结论没有来源，不纳入正文。

### 3. 证据驱动起草

按“事实 → 方法 → 结果 → 解释 → 验证/边界”展开：

- 清楚区分题目给定条件、建模假设、计算得到的结果和作者解释。
- 对关键公式解释变量、含义、约束和适用条件，不以公式堆砌代替论证。
- 对每个数值结果说明它代表什么、与目标或决策的关系，以及对应产物的位置。
- 使用可复核的表述，例如“依据表 3 的结果”“由 `表格/xxx.csv` 的字段……得到”；不可把文件名或未核实路径伪装成正文证据。
- 已采用的图必须以 Markdown 图片语法实际嵌入正文，已采用的表必须以 Markdown 表格实际呈现关键数据；仅写图号、表号、源路径或“见附录”不算采用图表。

### 4. 去 AI 味与可读性修订

在事实稿完成后，按内嵌 `humanizer-chinese-math-modeling/SKILL.md` 做受约束的表达修订。优先删除空泛套话、重复总结、无来源的程度副词和模板化连接词；保留计算逻辑、证据锚点和原有结论强度。不得为了“自然”而改动任何事实。

### 5. 终稿审查

逐项核对：

- 当届规范要求是否满足，未确认的规范项是否显式标出；
- 各小问是否有任务、模型、结果、解释与验证/边界；
- 正文的数字、表图、公式、结论能否回溯到建模证据；
- 图表、引用、附录编号是否互相一致；已采用图片是否真实嵌入并能通过相对路径打开，表中数值、单位与来源表是否一致；
- 每个有候选图表的已完成小问，是否记录了“采用”或“不采用”的理由；
- 是否存在未经证据支持的效果宣称、验证结论或参考文献；
- 去 AI 味修订是否保持原有模型、变量、数据、引用与结论边界。

## 交付规则

所有新生成内容只写入 `<项目根目录>/report_output/`。默认交付如下：

```text
report_output/
├── 报告.md                         # 草稿、完整报告或用户指定的章节；实际嵌入已采用图片和表格
├── 图片/                           # 仅复制正文实际采用的图片
├── 表格/                           # 仅复制正文实际采用或用于复核的原始表格
├── 报告证据映射.yaml               # 有效 YAML：正文结论、图片/表格与建模产物的对应关系
├── 写作审查.md                     # 规范、事实一致性、图表采用、结构与语言审查结果
└── 待补充材料.md                   # 仅在存在缺失或待核对内容时创建
```

- 最终提交格式（如 DOCX、PDF、LaTeX 或指定模板）以当届 `规范N` 和用户要求为准；未明确要求时，先交付可审阅的 `报告.md`，不要擅自声称已满足某种提交格式。
- `报告证据映射.yaml` 必须是可解析的 YAML，不得在 `.yaml` 文件中写 Markdown 标题或表格。至少记录 `sections`（章节/小问、正文结论摘要、验证状态）、`artifacts`（源路径、输出相对路径、类型、报告图/表号、使用方式、支撑结论）及 `open_items`。每一张正文图片和每一张正文表均需有一条 `artifacts` 记录。
- `写作审查.md` 至少记录：读取的规范文件、适用/未适用条款、证据一致性结果、图表候选清单与采用/未采用理由、结构检查、去 AI 味修订边界与遗留风险。
- 若仅请求一个章节，则只创建该章节对应的 Markdown 文件，并仍提供必要的证据映射和待核对说明；不得覆盖已有完整报告。

完成时向用户简要说明：已读取哪些材料、生成了哪些文件、哪些内容仍需建模或用户补充后才能定稿。
